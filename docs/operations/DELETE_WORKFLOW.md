# 削除例外ワークフロー

削除は例外操作である。通常更新では`DELETE_MANIFEST.txt`を空（コメントのみ）にする。

## 1. 基準を固定する

1. GitHubの最新コミットを確認する。
2. `Code → Download ZIP`で取得したソースを調査基準にする。
3. Pagesの反映は待たなくてよい。

## 2. 削除しない代替案を確認する

- 分割
- 移動
- 参照切替
- 生成防止
- 索引からの除外
- 非推奨化

代替案で解決できる場合は削除しない。

## 3. 影響を調査する

削除候補ごとに以下を確認する。

- HTML、JavaScript、PHP、Python、JSONからの参照
- マニフェスト、スキーマ、テスト、fixtureからの参照
- 動的に組み立てられるパス
- 生成元・生成先の関係
- 代替先
- 復旧方法

## 4. 人間の個別承認を作る

`DELETE_APPROVAL.json`に、対象ごとに次を記録する。

- 完全一致パス
- 許可カテゴリ
- 削除が必要な理由
- 削除しない代替案を採用できない理由
- 影響範囲
- 復旧方法

一般指示は承認として扱わない。

## 5. 今回分だけをマニフェストへ記載する

`DELETE_MANIFEST.txt`には、今回実際に削除するパスだけを1行1件で書く。
過去に削除済みのパスを再掲しない。


## 保護領域の二段階削除

保護領域を削除する場合も既定拒否は維持する。保護削除を含む更新では、`DELETE_APPROVAL.json` の対象entryに
`"protected_delete": true` を明示しなければintegrity checkerは拒否する。

このフラグはGitHub削除実行の承認そのものではない。更新ZIPが「保護削除を要求する更新」であることを機械的に宣言するための印である。
実際の配置時にはStudioで次の2つを人間が別々にONにする必要がある。

1. 通常の削除許可
2. 保護領域削除許可

したがって、保護削除は `DELETE_APPROVAL.json` の完全一致パス承認 + Studio通常削除許可 + Studio保護領域削除許可の全てが揃った場合だけ実行できる。

削除判定・削除ポリシー・Studio削除機構そのものを削除対象にすることは、保護削除許可があっても禁止する。

## 6. 機械検査

```bash
python3 tools/inspection/run.py full --context update --fail-fast
```

必須条件:

- `DELETE_MANIFEST_OK`
- `BLOCKED 0`
- 削除件数と確認画面の列挙件数が一致
- 保護領域を含まない
- 承認ファイルの対象と完全一致

## 7. 配置

1. Studioで実削除一覧を確認する。
2. 人間が削除許可を有効化する。
3. 確認画面でパスを再確認する。
4. 単一Commitで配置する。

削除機構を変更した場合は、まず機構だけを配置し、ページ更新後の別更新で削除する。

## 8. 完了確認

同じ更新ZIPで再確認し、次を満たすこと。

```text
ADD 0 / MODIFY 0 / DELETE 0 / BLOCKED 0
```

大きな削除や構造変更後は、GitHubから最新ZIPを取得し、次の正式基準にする。

## ソース基準へ混入した非永続ファイルの除去

`system-file-policy.json`導入前にGitHubへ混入した更新専用制御ファイルや成果物は、
`delete-policy.json`の`source_cleanup_exact_paths`へ完全一致パスで登録したものだけ削除できる。

この例外は通常の削除許可ではない。登録外の制御ファイル、保護領域、成果物は引き続き拒否する。
削除検査機構の変更と実削除は別々の更新で行う。
